# FE coordination points / limitations surfaced during this implementation

Captured here so they can be lifted into the PR description at finishing time.

## 1. Auto-scroll to bottom on streaming responses (open)

**Symptom:** when the AI streams its reply into the contextual chat, the chat does not auto-scroll. The user has to scroll manually to follow new tokens.

**Root cause (iOS side, confirmed):** the FE renders the chat inside an internal scrollable `<div>`. The WKWebView's outer `scrollView.contentSize` does not change as the FE writes new tokens — observed in build 14 logs: `contentSize {402, 292} → {402, 292}` repeats for the entire stream while the assistant types. iOS-side `NSKeyValueObservation` on `scrollView.contentSize` is therefore a dead end.

**Why it isn't visible in other surfaces:** the omnibar / full-tab duck.ai surface (URL `https://duck.ai/chat?duckai=4` — no `placement=sidebar`, no `chatID` initially) auto-scrolls correctly. Whatever the FE does there should also fire here, but apparently doesn't on the contextual surface (URL `…&chatID=…&nativeInput=1`).

**Action item:** FE team to make auto-scroll-to-bottom behaviour consistent across surfaces, or expose a JS message that lets iOS trigger it. (Considered an iOS-side `MutationObserver` JS injection workaround but punted — FE is the right home for chat scroll.)

## 2. `placement=sidebar` legacy triggers FE composer (resolved iOS-side)

**Symptom (interim):** with the flag on, both the FE-rendered composer and the native UTI were visible stacked. The URL had `placement=sidebar` from the half-sheet path, which the FE treats as "iOS hasn't replaced the composer yet, render mine".

**Resolution:** flipped `supportsNativeChatInput` in the JS config (`AIChatUserScriptHandling.getAIChatNativeConfigValues`) to `true` for the contextual mode when `unifiedToggleInput` is on. FE then suppresses its composer regardless of URL params.

**Action item (cleanup, optional):** The `placement=sidebar` URL path triggering FE composer is fine semantically (it's a legacy default), but means FE has two "is there a native input" signals (the URL param `nativeInput=1` we added per the original design, and the JS config `supportsNativeChatInput` we now drive). Long-term the FE could collapse to just the JS config, since URL params can race with iOS dependency injection. Not blocking.

## 3. FE-side bottom padding (suspected, not fully validated)

**Symptom (early builds):** even with the FE composer suppressed, the contextual chat showed visible empty space below the last message before the native UTI bar — as if the FE reserved its old composer's height as bottom padding.

**Status:** since stripping `placement=sidebar` from the loaded URL in build 11, this seems reduced. Should be validated once auto-scroll (#1) is also fixed — auto-scroll being broken makes "extra bottom space" hard to distinguish from "you're not at the bottom of the conversation".

**Action item:** FE team to confirm there's no static bottom padding reserved when `supportsNativeChatInput=true` (and to stop reserving it if there is one).

## 4. `nativeInput=1` URL param semi-redundant (informational)

The original spec called for iOS to set `nativeInput=1` on the contextual chat URL as the FE's signal to suppress the composer. We added it (and still send it). In practice, the suppression was driven by the JS config (#2), not the URL param. The URL param is harmless but potentially redundant — FE team can decide whether to keep honoring it or remove it. Two-signal redundancy is fine for safety; collapsing to one is cleaner.

## 5. `submitAIChatPageContext` push not merged into next prompt when composer suppressed (resolved iOS-side, FE coordination needed)

**Symptom (build 30):** with the native UTI active, the user manually attaches a page via the chip placeholder. iOS pushes the collected context to the FE via `submitAIChatPageContext` (verified in logs: `Pushing collected context to contextual chat for FE delivery` followed by `[PageContext] Context received - title: …, content: 9492 chars`). User then submits a prompt asking about the page. The AI responds as if no page is attached — it has no awareness of the article content.

**Root cause:** the contextual chat sends two separate JS messages:
- `submitAIChatPageContext` (push) — broadcasts the attached context.
- `submitPrompt` (RPC) — sends the user's prompt with optional `pageContext` in the payload.

The iOS prompt-submission path through the native UTI was using `AIChatUserScript.submitPrompt(_:images:modelId:tools:reasoningEffort:)` (the multi-modal variant), which omitted `pageContext` from the payload — even though the underlying `AIChatNativePrompt.queryPrompt` API supports it. So the FE was relying on its own merging logic (i.e. "remember the last `submitAIChatPageContext` push and apply it to the next prompt"), which evidently does not run when `supportsNativeChatInput=true` (the FE composer-suppression mode we drive — see #2).

**Resolution (iOS-side, build 31):** `AIChatUserScript` now caches the most-recently-pushed `pageContext` (`lastPushedPageContext`) and includes it directly in the prompt payload on every `submitPrompt`. Both signals are sent — the JS push and the inline payload — so the FE can use either. This restores the legacy FE-composer contract where the prompt payload always carried its own context.

**Action item (FE):** when `supportsNativeChatInput=true`, `submitAIChatPageContext` push should still merge into the next prompt's context. Our redundant-signal fix means the FE *can* fix this without breaking iOS, but currently the iOS-side cache is doing the work that the push contract implies. Long-term, FE choosing one source of truth (push OR inline) and documenting it would let iOS drop the redundancy.

**Action item (iOS, follow-up):** add a unit test for `AIChatUserScript` covering: `submitPageContext(ctx)` → `submitPrompt(...)` → assert payload contains `pageContext: ctx`. And: `submitPageContext(nil)` (chip detached) → `submitPrompt(...)` → assert payload has nil `pageContext`. Currently only covered by manual testing.

## 6. Initial attached-context carry-over from half-sheet (likely OK, worth a sanity check)

**Setup:** the user opens the half-sheet on a page, attaches it (FE-driven via `getPageContext` callback), confirms → contextual chat opens with the chip already in attached state (`initialAttachedContext` carried via `sessionState.latestContext`). User types and submits a prompt as their first action.

**Concern:** the iOS host doesn't proactively push the carry-over context to the contextual chat's FE on bootstrap — it just hands the context to the chip view-model for display. The FE is expected to have the context already (the half-sheet flow having written it before transition, and/or the chat session reload restoring it via `chatID`).

**Status:** flow appears to work in manual testing — the AI responds with awareness of the attached page on the very first prompt after carry-over. So there's an existing pathway that delivers the initial context to the FE. Not validated end-to-end in this branch, but no symptom reported.

**Action item (iOS, defensive):** if validation reveals the carry-over context isn't reaching the FE in some edge cases, the host could push `initialAttachedContext` once at install time, parallel to how chip-tap pushes manually-collected context. Holding off until needed.
