# Review instructions

What to flag when reviewing this repository. `CLAUDE.md` and the rules it points
to cover how to *write* code here; this file covers what to *report*.

## Severity

Reserve 🔴 Important for findings that would ship broken behaviour, leak or lose
user data, or block a release:

- Incorrect logic, broken edge cases, races, retain cycles
- Privacy regressions: user data reaching logs, pixels, or crash reports
- A missing or wrong pixel definition — these break the remote data pipeline
  silently, with no build or runtime failure
- A dependency version change that leaves a tracked lockfile stale
- A hand-edited embedded privacy config or tracker data file

Style, naming, structure, and refactoring suggestions are 🟡 Nit at most.

## Cap the nits

Report at most five Nits per review. If you found more, add "plus N similar
items" to the summary instead of posting them inline. If everything you found is
a Nit, lead the summary with "No blocking issues".

## Do not report

- Anything CI already enforces: SwiftLint, `npm run validate-pixel-defs`,
  `scripts/check_wide_event_consistency.mjs`,
  `scripts/check_wide_event_schema_immutability.mjs`, and the Danger check that
  hard-fails a new case in `iOS/Core/PixelEvent.swift`
- Generated files, including anything under `wide_events/generated_schemas/`
- A `Package.resolved` diff that differs only in `originHash` — it churns across
  Xcode versions and means nothing on its own
- The `SnapshotReferences` submodule pointer
- Existing code in a file the PR touches but did not itself modify
- `TEMPLATE.json5` files — scaffolds with deliberately placeholder values

## Verification bar

A behaviour claim needs a `file:line` citation in the source, not an inference
from a name. This repo carries many similarly named types across `iOS/`,
`macOS/`, and `SharedPackages/`; confirm you are reading the one the diff
actually builds against before reporting.

## Re-review

After the first review of a PR, report 🔴 Important findings only and suppress
new Nits, so a one-line fix does not accumulate rounds of style comments.

## Pixels and wide events

These have detailed rules of their own, kept separately to stay out of the
context of reviews that do not need them.

**If this PR adds or modifies a pixel event, a wide event, or any file under
`iOS/PixelDefinitions/` or `macOS/PixelDefinitions/`, read `REVIEW-pixels.md` at
the repository root before reporting.**

## Unit tests

A new Swift Testing test (`@Test`) must declare a timeout. The framework default
is 60 minutes, which can outlast the CI workflow itself.

## Dependency changes

When a PR changes a Swift package dependency's pinned version, every tracked
lockfile that resolves it must be re-resolved in the same PR. The tracked
`Package.resolved` files are the source of truth:

- `iOS/DuckDuckGo-iOS.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`
- `macOS/DuckDuckGo-macOS.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`
- `SharedPackages/*/Package.resolved` and the various `*/LocalPackages/*/Package.resolved`

The workspace-level `DuckDuckGo.xcworkspace/xcshareddata/swiftpm/Package.resolved`
is **not** tracked — it is gitignored because Xcode regenerates it on open and
nothing in CI consumes it. Do not reference it or expect it in a diff.

Flag:

- A dependency the PR adds or modifies that is pinned with a *range* rather than
  `exact:` — `from:`, `.upToNextMajor(from:)`, `.upToNextMinor(from:)`, or a
  range operator. Recommend rewriting as `exact: "x.y.z"`.
- A `branch:` dependency added or modified: a floating reference is not
  reproducible. A `revision:` commit SHA is an acceptable precise pin, but
  prefer `exact:` once the dependency has a tagged release.
- A changed version requirement with a stale downstream `Package.resolved`.
  Packages reference each other by local path — many resolve
  `BrowserServicesKit` that way — so a bump ripples into consumers' lockfiles.
  Advise running `./scripts/resolve-project-dependencies.sh` and committing the
  result. This is common on Dependabot PRs, which update only
  `SharedPackages/BrowserServicesKit`.

Do not flag a `Package.swift` change that alters no dependency version, such as
adding a target or product. Do not flag a version change to a dependency outside
the app build graph; if you cannot tell whether it reaches the apps, ask rather
than require.

## Embedded privacy config and tracker data

The app bundles a snapshot of the remote privacy configuration and tracker data
set so it has a fallback on first launch and offline. These files are fetched
from the CDN and regenerated by `scripts/update_embedded.sh`. They are not meant
to be hand-edited and are not the source of truth. Each is paired with a
provider recording its `embeddedDataETag` (md5) and `embeddedDataSHA` (sha256),
and a guard test fails when the two drift apart.

| Embedded data file | Paired provider |
|---|---|
| `iOS/Core/ios-config.json` | `iOS/Core/AppPrivacyConfigurationDataProvider.swift` |
| `iOS/Core/trackerData.json` | `iOS/Core/AppTrackerDataSetProvider.swift` |
| `macOS/DuckDuckGo/ContentBlocker/Resources/macos-config.json` | `macOS/DuckDuckGo/ContentBlocker/AppPrivacyConfigurationDataProvider.swift` |
| `macOS/DuckDuckGo/ContentBlocker/Resources/trackerData.json` | `macOS/DuckDuckGo/ContentBlocker/AppTrackerDataSetProvider.swift` |

Both guard tests are named `testWhenEmbeddedDataIsUpdatedThenUpdateSHAAndEtag`.

Flag:

- An embedded data file modified without its provider's `embeddedDataSHA`
  updated in the same PR — the paired guard test will fail on CI. This signature
  almost always means the file was hand-edited, because `update_embedded.sh`
  always rewrites both constants in the same pass. Ask the author to revert the
  hand-edit and regenerate.
- A hand-edit to `ios-config.json` or `macos-config.json` that adds, removes, or
  changes a feature or subfeature as part of a feature change. **Editing the
  embedded config does not change the remote configuration and does not enable a
  flag for users.** It is only the local fallback: the app fetches the live
  config from the CDN at runtime, and the embedded copy is overwritten on the
  next regeneration, so a flag added only here is invisible to release
  management. A real rollout must land in
  https://github.com/duckduckgo/privacy-configuration. Frame this as a reminder
  rather than an error — occasionally seeding a default-off flag into the
  snapshot is legitimate.

Do not flag a wholesale regeneration: the file replaced and the provider's
`embeddedDataETag` and `embeddedDataSHA` updated together, typically titled
"Update embedded files" with no unrelated source changes. That is
`update_embedded.sh` doing its job, and the content came from remote — do not
attach the "does not reach remote" reminder to it. Do not flag a provider
refactor that leaves its `Constants` block alone when no embedded file changed.
