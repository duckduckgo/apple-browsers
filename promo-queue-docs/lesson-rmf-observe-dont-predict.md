# Observe actual RMF visibility rather than predicting schedules

Ben S's scope-thread objection ("there's no reliable way to predict when an RMF will appear or what type it will be") is real — RMF rules re-evaluate on config download / 24h invalidation (`RemoteMessagingConfigProcessor`; confirmed again in the Fire Mode thread). The useful macOS design principle is to observe current state rather than predict future schedules.

macOS's `RemoteMessagePromoDelegate` observes selected supported-message presence, not actual window visibility. That is sufficient for its current policy but should not be copied literally to iOS: iOS creates a messages model per NTP, and a scheduled or selected message may be off-screen. Treating selection as visibility would unnecessarily suppress launch modals. Conversely, relying only on a store notification leaves a race while a modal is committing.

Why it mattered: iteration 1 observes manager-owned modal commitment and renderer eligibility rather than predicting RMF schedules. Q2 serializes both promo types through one global identity-bearing owner. `PromoCoordinationService` owns one logical RMF session, authorizes one renderer, and retains the lease until an exact removal terminal plus one settlement turn. Existing host exposure still tells the service which renderer is eligible; the old per-model gate/mount ownership graph is gone. Q3 paces confirmed appearances outside RMF: modal→RMF and RMF→RMF wait 10m; RMF→modal waits 24h; modal→modal keeps the existing remotely tunable interval. Modal history is written only at confirmed UIKit/adoption presentation, and RMF queue history only on the first accepted physical appearance of a logical session. A same-session renderer handoff does not restart that timestamp, while ordinary RMF accounting remains per accepted presentation. A blocked RMF waits without consumption. Cooldown passage is not an event, so reconsideration occurs only at configuration, renderer, lifecycle, host-readiness, successful-release, or removal-settlement checkpoints. The implementation adds no Promo Queue telemetry.
