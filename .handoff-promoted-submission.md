## The problem

`AIChatContextualSheetViewController` is built to be *typed into*: it opens at the medium
detent on its start surface, and its input bar renders pre-submit until it rebinds to the
chat's user script. A1 added a second caller — the floating input, which *submits a prompt
and then opens the sheet*. Reusing the same controller for that produced three artifacts,
each patched with a flag on the shared path:

| Artifact | Current patch |
|---|---|
| Opened at medium, grew to large | `opensOntoSubmittedChat` picks the initial detent |
| Fell back to the start surface (session still reported `.nativeInput` when the sheet was built) | `isAwaitingSubmittedChat` treats that state as stale and ignores it |
| Mounted the input while it still rendered its pre-submit self, page chip and all | mount deferred to the chat-live reveal |

The flags are individually coherent but they are three answers to one mismatch: a sheet
opened onto an *answer* is not the same surface as a sheet opened to be *typed into*.

## Hard constraint

**The old flow must keep working.** With `aiChatContextualFloatingInput` off there is no
floating input, the sheet is typed into, and every behaviour above is correct as-is. Any
separation must be **additive, not a replacement**. iPad always gets the old sheet
regardless of the flag.

## Suggested direction (not decided — brainstorm it)

The two surfaces differ in initial detent, initial content, and when the input may mount.
That smells like one type per entry point over a shared body, rather than one type with
three booleans. Worth weighing against: how much of `AIChatContextualSheetViewController`
is genuinely shared, and whether a protocol/strategy for "how does this sheet start"
is lighter than a split.
