Pre-iteration baseline: two paths that never talked

Before coordination, launch modals and NTP RMF cards were driven by two independent pipelines over the same foreground moment. Neither knew the other had committed, so both could end up on screen.

Launch-modal pathNTP / RMF pathFailure mode
Fig 1 · The pre-iteration pipelines. The modal chain evaluated once per eligible foreground; every NTP instance independently mapped RMF view models from shared scheduled state. Scheduled, selected, rendered, and visible are four different states — and the baseline had no app-level source saying “an RMF card is rendered in an active NTP.” TECH_DESIGN_FINAL.md · Problem Statement
02

Why a permission check is not enough

A Boolean “may I show?” check plus a later visibility report leaves two real windows where both surfaces get admitted. Both existed in the pre-iteration code; the lease model was chosen specifically to close them.

Fig 2a · Race 1. Publication of the RMF view model and the card’s .onAppear happen in different run-loop turns. A check-based coordinator lets the modal commit inside that gap. A lease closes it: the render gate atomically acquires the lease before the card is even constructed, so one side always loses the exchange. TECH_DESIGN_FINAL.md · Why a Lease Model (1)
Fig 2b · Race 2. In the baseline, commitment happened before a fixed delay that could not be revoked. The implementation makes scheduling generation-aware and revalidates the attempt, provider, and prepared configuration immediately before presentation; a failed attempt keeps at most one prepared configuration for a later foreground without holding the RMF slot. TECH_DESIGN_FINAL.md · Why a Lease Model (2) · Change Inventory
03

The lease model

One app-scoped, main-actor arbiter owns exactly one invariant. It tracks who holds the slot; the Manager keeps the modal's detailed lifecycle. Admission on either side is a check-and-mutate lease acquisition — never a Boolean query followed by a later report.

Fig 3 · Detailed modal state stays in the Manager; mutual exclusion stays in the arbiter. The same modal lease remains held through evaluating, committed, and presentation-active. The arbiter only knows that the modal side holds the slot, so the NTP treats every modal phase the same. TECH_DESIGN_FINAL.md · Ownership · Behavioral Rules 2–5
04

Where the arbiter sits

Existing components keep their policy ownership. The arbiter is inserted at two seams: before provider evaluation on the coordinated modal side, and in front of card construction on the NTP side.

Existing modal pathExisting NTP / RMF pathNew arbiterNew seam
Fig 4 · Insertion points, not replacement. Three pieces are new (arbiter, render gate, checkpoint reconciliation); two pieces are hardened (scheduler, NTP activity reporting). Everything is behind the iOS promoPresentationCoordination feature flag and bypassed when it is off. TECH_DESIGN_FINAL.md · Ownership · Design-Level Change Inventory
05

The two orderings, end to end

Whichever side wins admission, the other waits without burning state — a blocked provider is never queried, a blocked card is never marked shown.

Fig 5a · RMF wins. Admission fails before any provider runs, so nothing is recorded anywhere — important because Default Browser burns “seen” state during eligibility itself. An undismissed card defers modals on each foreground where it is rendered in the active NTP (bounded by dismissal, expiry, or config replacement). TECH_DESIGN_FINAL.md · Behavioral Rule 1
Fig 5b · Modal wins. The evaluation lease blocks RMF before provider selection. The Manager moves the attempt to committed before the delay while the arbiter keeps the same lease held. A presentation-active modal is never retracted for RMF; release happens at the first checkpoint after the root is gone (the accepted delay), and nested child flows do not finish the promo session. TECH_DESIGN_FINAL.md · Behavioral Rules 2–5
06

Many NTP instances, one truth

NTPs exist in more places than tabs — the suggestion tray and input container build live instances over the same shared state. Only an on-window NTP whose composed owner, readiness, visibility, coverage, and gate-mount state is renderable may hold a lease.

Fig 6 · Per-instance leases. This is why “selected” must not mean “visible”: with one shared candidate and N live models, treating selection as visibility would let an off-screen tray NTP suppress launch modals indefinitely. TECH_DESIGN_FINAL.md · Behavioral Rules 6, 9 · Problem Statement
07

Shown accounting: before and after

In the pre-coordination baseline, shown fired at map time, again on appearance, and again on refreshes — and unique could double-fire. PR 2 ties normal shown to one admitted render-session appearance; PR 3 adds the shared atomic unique winner.

Fig 7 · The accounting correction across PRs 2–3. Once a card can be blocked, map-time “shown” is wrong because it starts expiry for a never-rendered card. PR 2 gates normal shown behind admitted onDidAppear; PR 3 adds the shared reservation that makes unique shown atomic across NTPs. Feature off keeps the baseline accounting path unchanged. What this appendix should leave you with

The design is a narrow insertion, not a rewrite: one in-memory arbiter enforcing one invariant, one new gate in front of the card, a hardened scheduler, and checkpoint-based release. All seven providers keep their eligibility policy, priority, cooldown, and accounting ownership while their adapters revalidate delayed work. RMF selection stays in its current owner, and the whole path remains removable behind the feature flag if iteration 3 picks a different owner.
