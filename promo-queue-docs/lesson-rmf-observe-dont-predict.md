# Observe actual RMF visibility rather than predicting schedules

Ben S's scope-thread objection ("there's no reliable way to predict when an RMF will appear or what type it will be") is real — RMF rules re-evaluate on config download / 24h invalidation (`RemoteMessagingConfigProcessor`; confirmed again in the Fire Mode thread). The useful macOS design principle is to observe current state rather than predict future schedules.

macOS's `RemoteMessagePromoDelegate` observes selected supported-message presence, not actual window visibility. That is sufficient for its current policy but should not be copied literally to iOS: iOS creates a messages model per NTP, and a scheduled or selected message may be off-screen. Treating selection as visibility would unnecessarily suppress launch modals. Conversely, relying only on a store notification leaves a race while a modal is committing.

Why it mattered: iteration 1 observes manager-owned modal commitment/visibility and per-NTP actual RMF visibility/render permission. PR 3 commit `06a2417373` paces confirmed appearances without predicting RMF selection: modal→RMF and global RMF→RMF wait 10m; RMF→modal waits a fixed 24h; modal→modal keeps the existing remotely tunable interval. Modal history is written only at confirmed UIKit/adoption presentation, and RMF history only on the first appearance of an admitted render session. A blocked RMF waits without consumption until both checkpoint release and cooldown admission; one timer retries an active candidate at the earliest 10-minute boundary. Modal retry remains foreground/checkpoint-driven. The implementation adds no Promo Queue telemetry; that is a separate project. This remains compatible with a future RMF-owned, client-owned, or hybrid design without registering RMF as a macOS-style `ExternalPromo` today.
