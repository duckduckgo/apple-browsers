iOS Promo Queue

A single app-scoped admission boundary coordinates launch-promo sheets and Remote Messaging Framework cards while keeping presentation details inside their existing modal and New Tab Page systems.

System intent

One decision point, existing renderers

Launch promos and RMF cards previously made their presentation decisions in separate subsystems. Promo Queue adds one shared owner and a directional cooldown policy, then lets each subsystem continue to select, build, present, dismiss, and account for its own content.

User problem

A launch-promo sheet can cover an RMF card, or an RMF card can remain published while a sheet is admitted. That overlap dilutes both prompts and produces timing-dependent behavior across app activation and NTP entry paths.

The coordination boundary must be app-scoped because both presentation families can be reached from more than one physical view.

Success criterion

At most one presentation family owns the promo slot. Modal admission happens before stateful provider evaluation; RMF admission happens before a message is published to any NTP renderer.

Three production layers

The implementation is arranged as a linear stack. Each layer adds one coherent architectural capability while retaining the behavior established below it.

One graph assembled at launch

Interaction model

Admission precedes publication or provider work

Both flows use the same owner, but they place the gate at the point that avoids domain side effects: before modal provider evaluation and after RMF selection and renderability checks but before shared-source publication.

Ownership semantics

A small, identity-safe lifecycle

The arbiter stores one typed owner. Acquisition identities separate consecutive ownerships of the same message ID, and weak tokens allow abandoned owners to be recovered at the next admission checkpoint.

  1. Select The domain identifies content and verifies that it can render.
  2. Acquire The service applies cooldown and grants a typed identity.
  3. Publish or present The owning domain exposes content only after admission.
  4. Confirm First RMF appearance records accounting once per ownership.
  5. Release Background, replacement, dismissal, or teardown frees the slot.

Identity, not message ID alone

An RMF acquisition carries a unique identity. Appearance and release callbacks must match it, so callbacks from an earlier ownership cannot affect a later acquisition of the same message.

Weak-token recovery

The owner token is weak. If its domain object disappears without an explicit release, the next acquisition prunes the dead owner and can make progress.

Exact-root modal ownership

Modal ownership follows the exact controller committed by the manager. A later checkpoint reconciles its attachment state and releases only that presentation identity.

Background teardown ordering

The shared RMF source first disables admission, clears its checkpoint policy, unpublishes the message and emits the source update, then releases the lease. Foregrounding re-enables admission; a normal checkpoint performs fresh selection and acquisition. No timer or background retry queue is involved.

Directional cooldowns

Incoming family Prior history Boundary Meaning
RMF Last modal appearance 10 minutes An NTP card does not immediately follow a launch-promo sheet.
RMF Last confirmed RMF appearance 10 minutes Repeated NTP activation does not repeatedly surface RMF content.
Modal Last confirmed RMF appearance 24 hours A launch-promo sheet does not follow a recently seen RMF card.

The modal manager’s established per-provider cooldown rules remain in force after queue admission. RMF history advances only on a confirmed first appearance, not merely on selection or publication.

Controlled adoption

Legacy and coordinated behavior is selected once at startup

promoPresentationCoordination is sampled when the app-services graph is constructed. The service stores the resulting immutable mode, so changing the local flag takes effect after relaunch rather than migrating live ownership.

Concern Legacy mode Coordinated mode

Modal entry The service delegates to the established modal manager behavior. The shared slot and directional cooldown are checked before provider evaluation.

Current coordinated activation checkpoints

Standard NTP, the legacy/iPad suggestion tray, OmniBar editing through SuggestionTrayManager, and unified input each prepare the same shared source when coordinated mode is active. The selected trigger policy is pinned for the ownership: an after-idle attempt may fall back to no-trigger selection, and later mounts do not replace that decision.

Surface integration

A future NTP surface joins at the shared-source seam

Coordination is deliberately independent of renderer visibility and coverage. A new RMF-capable surface consumes the existing source and adds one activation checkpoint; it does not become another queue owner.

What the surface supplies

  • Reuse the app-scoped HomePageConfiguration graph.
  • Call prepareForNTP at its real activation checkpoint.
  • Consume the shared message through NewTabPageMessagesModel.
  • Forward first appearance with the coordinated view identity.

What the surface does not report

  • Renderer visibility, percentage coverage, or scrolling state.
  • Mount and unmount retain counts.
  • Cross-renderer ownership handoff.
  • Lifecycle callbacks to the central coordinator.
  • Retry timing, fairness, or scheduling state.

Source ownership is the scaling mechanism

Multiple physical views may mount the same RMF message. Because the shared source owns one lease and one acquisition identity, duplicate mounts do not multiply queue state, and appearance accounting remains once per ownership.

Design boundaries

Deliberately small coordination state

Promo Queue centralizes only the cross-family decision. Selection, rendering, presentation, and product-specific cooldown rules stay with their established owners.

One typed slot

The arbiter stores modal or RMF, never renderer-level substate. Ownership identities make release and appearance idempotent.

Startup-latched mode

A relaunch switches graphs cleanly, avoiding live migration, re-adoption, and lease invalidation machinery.

Checkpoint-driven progress

Launch, NTP activation, dismissal reconciliation, foregrounding, and background teardown are sufficient progression points.

First owner wins

A successful acquisition pins its trigger context until release. A competing family waits for a later natural checkpoint.

Explicit modal precedence

The modal manager preserves a single explicit provider order, so shared admission happens once before the established launch-promo selection sequence.

No renderer state machine

The service does not model screen coverage, physical mounts, handoff, visibility, timers, fairness, or a retry scheduler.

Internal observability

Prompt Coordination uses the production graph

The internal debug destination reads passive snapshots from the same service, arbiter, and history stores used by the app. It does not create a parallel coordinator.

Queue state

Startup mode, current modal or RMF owner, ownership identity, and RMF appearance state.

Cooldown history

Modal and RMF timestamps plus the directional boundaries derived from them.

Explicit controls

Separate modal and RMF cooldown resets routed through the production stores.

Feature-flag changes are process-latched, so the screen states that a relaunch is required before the displayed mode changes.
