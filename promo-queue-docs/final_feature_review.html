User problem and success criterion

User problem

Launch-promo sheets and NTP remote messages previously made independent presentation decisions. They could overlap, mutate state before they had permission to show, or require renderers to coordinate view visibility and handoff.

Success criterion

One app-scoped slot admits either a launch modal or one shared-source RMF. Admission occurs before stateful provider evaluation/publication; background releases; progress occurs only at natural checkpoints; renderers never report visibility, coverage, handoff, or lifecycle.

Verified The coordinated implementation meets this criterion in code and focused tests. The verdict is blocked because disabling the feature does not fully restore untouched legacy behavior.

Future RMF surface integration

What a conditional container does

  1. Before activation-time eligibility, call prepareForNTP(openedAfterIdle:) once.
  2. Consume the shared HomePageMessagesConfiguration data.
  3. Observe the configuration-scoped content signal if it must reevaluate visibility after source changes.

A leaf renderer that receives an already-prepared source needs no Promo Queue call.

What it never reports

  • lease acquisition, confirmation, or release;
  • visible/renderable/covered state;
  • mount count or “last renderer” disappearance;
  • handoff, drain, or removal acknowledgement; or
  • foreground/background lifecycle.

Accepted simplifications

All accepted simplifications are present and justified: seven-provider scope; arbitrary-sheet coverage; off-NTP over-hold; fresh post-background acquisition/cooldown rules; brief duplicate mounts; no Fire/landscape lease rule; checkpoint delay/no fairness; lazy modal release; best-effort dismissal/unique shown; startup latch; no new telemetry; and expected lower regular-shown volume.

Reviewer hotspots and key decisions

Correctness hotspots

  • HomePageConfiguration.swift:245-335 — selection, pinning, retain-before-publish, teardown ordering.
  • PromoCoordinationService.swift:100-169 — admission before provider/source work.
  • PromoQueueLeaseArbiter.swift:156-251 — one owner, weak recovery, identity-safe release and appearance.
  • ModalPromptCoordinationManager.swift:163-204,244-264 — exact-root retention and lazy reconciliation.
  • MainViewController.swift:5553 — missing feature-mode guard.

Intentional boundaries

  • One modal identity; RMF needs a separate acquisition identity.
  • Source owns RMF; renderers only map and report existing actions/appearance.
  • Onboarding/renderability remain source policy, not arbiter state.
  • Background is a terminal; ordinary disappearance is not.
  • No timer, immediate handoff, fairness, force-owner debug control, or new pixel.
