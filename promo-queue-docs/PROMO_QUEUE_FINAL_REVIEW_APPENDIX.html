Purpose, scope, invariants, flag, and non-goals

Promo Queue prevents launch-modal promos and NTP Remote Messaging Framework (RMF) cards from appearing together. It is a narrow coordination layer: RMF still owns message targeting, content, persistence, and dismissal; the modal manager still owns provider ordering, modal policy, and UIKit presentation.

Scope

  • Launch modals and NTP RMF cards on iOS.
  • One main-actor owner across all NTP instances.
  • Standard NTP, suggestion-tray NTP, and unified-input/favorites NTP presentation contexts.
  • Directional cooldowns and local read-only diagnostics.

Core invariants

  • At most one global owner: modal or RMF.
  • Admission precedes provider evaluation or RMF card construction.
  • History records confirmed appearances, not intent.
  • Modal ownership ends at exact-root detachment.
  • RMF ownership ends after physical removal plus one main turn.

Non-goals

  • A generic promo scheduler, priority system, caps, or restoration.
  • macOS PromoService changes.
  • New telemetry, pixels, or rollout configuration.
  • Atomic unique-shown reservation.
  • Live feature-flag transitions.

Confirmed-appearance timestamp flow

RMF persistence failure semantics

  • Initial read failure means no known history and remains retryable.
  • A successful read—including nil—is cached; a later read failure uses the last successful value.
  • After a failed write, the attempted value remains authoritative in the current process; a relaunch sees only the last persisted value.
  • Diagnostic reads do not seed or mutate production fallback state.

PromoQueueCooldownPolicy.swift:48–145; PromptCooldownStore.swift:25–88.

Common developer workflows

Add a modal provider

  1. Conform to internal ModalPromptProvider and return a complete ModalPromptConfiguration.
  2. Implement a side-effect-free presentation-validity check for retained/fire-time revalidation.
  3. Conform to InvalidModalPromptReplacing only when replacement preparation is safe.
  4. Add the provider to ModalPromptProviders, factory construction, and the explicit priority array.
  5. Test selection order, no query before owner/cooldown, retained revalidation, fire-time invalidation, accounting, and exact-root lifetime.

ModalPromptProvider.swift:23–96; PromoCoordinationFactory.swift:43–80; PromoCoordinationService.swift:117–155.

Integrate a new NTP-covering surface

  1. Treat “RMF surface” as an NTP presentation context, not a new RMF destination.
  2. Give the hosted NTP a stable controller/model lifetime and surface ID.
  3. Feed owner, visibility generation, window attachment, cover state, and render location into the centralized exposure predicate.
  4. Use showHostedSurface: deactivate outgoing standard NTP before revealing incoming host.
  5. Use showNewTabPage: deactivate/hide hosted surface before reactivating the standard NTP; guard async completion with generation/identity.
  6. Test visible/hidden transitions, failed presentation, rapid reversal, multiple NTPs, pending animation completion, and physical removal.

NewTabPageViewController.swift:30–64, 276–315; integrations in MainViewController.swift:3159–3193 and unified-input sources.

Debug coordination

  1. Open the existing Modal Prompt Coordination debug screen.
  2. Confirm latched mode; a running graph does not follow live flag changes.
  3. Inspect singular owner identity, modal phase/pending state, app readiness, and live weak registration count.
  4. Inspect last confirmed source timestamps and derived next-eligibility boundaries.
  5. Remember: a boundary is not a scheduled retry. Trigger a documented checkpoint.
  6. For a stuck RMF, check host exposure, window attachment, gate mount, current owner, and outgoing physical-removal state in that order.

ModalPromptCoordinationDebugMenu.swift:24–216; PromoCoordinationService.swift:455–480.

Known tradeoffs and intentional limitations

DecisionBenefitCost / operational consequence
Process-latched flagOne internally consistent app graph; no mid-session migration states.Kill switch/local override takes effect only after a fresh process graph.
One global ownerSimple, strong no-overlap invariant across modal and every NTP.A hidden host that incorrectly retains ownership can starve all promos; a second RMF cannot appear while the first remains mounted.
Checkpoint-only cooldown retryNo timer lifecycle, persistence, or clock-change machinery.Eligibility can be delayed past the exact 10m/24h boundary until another real event.
Manual host integrationKeeps coordination independent of view-controller framework details.Not compiler-enforced; every future overlay/host must update the exposure/handoff seam correctly.
Cached Default Browser retained validationAvoids repeating an expensive external status query during retry.An external default-browser change after initial selection can leave the cached validation stale.
No atomic unique-shown reservationAvoids expanding core scope and RMF persistence behavior.The existing asynchronous unique-shown check/write can race across sequential configurations.
Local read-only diagnosticsUseful state visibility without influencing production decisions.No telemetry/pixels for fleet-level collision, fairness, or cooldown analysis.

Glossary

Promo Queue

The narrow iOS coordination system that arbitrates launch modals and NTP RMF cards. It is not a general scheduling framework.

Modal

A launch-time promotional UIKit presentation chosen by the existing ordered modal-provider system.

RMF

Remote Messaging Framework. It owns remote-message targeting, selection, content, dismissal, and its normal accounting/persistence.

RMF surface

Currently an NTP presentation context affected by overlays such as the suggestion tray or unified input. It is not a separately supported RMF destination.

Host exposure

Whether an NTP is the owning, visible, window-attached, uncovered, renderable presentation context. Exposure changes are admission/removal checkpoints.

Owner / lease

The arbiter’s one active identity and the consumer-held token that proves authority to clear it. Tokens release idempotently and stale tokens cannot clear replacements.

Admission

An identity-bound RMF capability returned only after ownership and cooldown checks. It confirms one appearance and later releases ownership.

Retained candidate

Selected modal or RMF work kept without presentation/accounting while blocked, so it can be revalidated at a later checkpoint.

Physical removal

The actual visual terminal after the SwiftUI card’s scale/opacity transition, not merely model withdrawal or onDisappear beginning.

Readiness token

An opaque identity for one full foreground cycle. Background rotates it; stale asynchronous callbacks cannot reopen admission.

Checkpoint

A real app/UI event that justifies reconsidering retained work: load, refresh, mount, exposure, readiness/lifecycle, owner release, or the standard modal pass.

Cooldown

A directional minimum interval derived from confirmed source-event timestamps. Crossing a boundary alone does not trigger work.
