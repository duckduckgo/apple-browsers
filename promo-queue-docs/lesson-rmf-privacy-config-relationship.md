# RMF and privacy-config are two separate static configs with a one-way dependency (privacy-config gates RMF; RMF can target on privacy-config flags)

RMF config and privacy config are **different files, different URLs, different repos** — neither is a live per-user backend; both are static JSON on `staticcdn.duckduckgo.com` shipped identically to everyone. RMF: `remotemessaging/config/v1/ios-config.json` (repo `remote-messaging-config`; URL set at `iOS/DuckDuckGo/RemoteMessagingClient.swift:43`) carries **message content + targeting rules**. Privacy config: `trackerblocking/config/v2/ios-config.json` (repo `privacy-configuration`) carries **feature flags**. The dependency is one-way — RMF reads privacy config; privacy config never references RMF, and the RMF JSON contains no structural reference to privacy config (keyword hits there are only message text like `ios_privacy_pro_exit_survey`). There are two concrete links:

1. **Gate / kill-switch.** Privacy config's `remoteMessaging` feature key turns the whole framework on/off. `PrivacyConfigurationRemoteMessagingAvailabilityProvider.isRemoteMessagingAvailable` = `privacyConfig.isEnabled(featureKey: .remoteMessaging)` (`RemoteMessagingAvailabilityProviding.swift:43`). If off, the pipeline short-circuits: `fetchAndProcess` returns early (`RemoteMessagingProcessing.swift:82`) and `RemoteMessagingStore` refuses reads/writes (~10 guards). Base `features/remote-messaging.json` is `state: disabled`; `overrides/ios-override.json` flips it to `enabled`, so RMF is **live on iOS**. Related privacy-config flags in the same family: `promoQueue` (whose iOS app flag maps to `iOSPromoQueueSubfeature.iOSPromoPresentationCoordination`; rollout is covered in `TECH_DESIGN_FINAL.md`), `additionalCampaignPixelParams`, `messageBridge`.
2. **Targeting.** RMF *rules* can match on privacy-config flag state via the `allFeatureFlagsEnabled` matching attribute (`schemas/ios/schema.json:425`; client `MatchingAttributes.swift:260` → `UserAttributeMatcher.swift:384`). The list it matches against is built on-device from `FeatureFlag.allCases.filter { featureFlagger.isFeatureOn(for: $0) }` at `iOS/DuckDuckGo/RemoteMessagingConfigMatcherProvider.swift:165` — i.e. the feature flagger, whose source of truth is privacy config.

RMF itself is a **static config + client-side rules engine**: the JSON has `messages` + `rules` (rules referenced by id via `matchingRules`/`exclusionRules`), and `RemoteMessagingConfigMatcher.evaluate()` picks at most one message on-device. The attribute vocabulary is **hardcoded in the client** (`MatchingAttributes.swift` — locale, os, appVersion, daysSinceInstalled, favorites, subscription status, `allFeatureFlagsEnabled`, …), so a config can only use attributes the installed app version understands — **new targeting dimensions require a client release, not just a config edit**. (For *when* it re-evaluates and why that forces the observe-not-predict design, see [[lesson-rmf-observe-dont-predict]].)

Why it mattered: this is the definitive answer to "how does RMF relate to privacy config" — they're cleanly separated (privacy config answers "is this system on?"; RMF answers "what message, to whom, where?"), joined only by the one-way gate + targeting links above. The targeted iteration-1 coordinator does not predict or duplicate that evaluation. RMF continues to select and persist candidates; the coordinator grants only final visibility against committed launch-modal state. The `promoQueue.features.iOSPromoPresentationCoordination` privacy-config subfeature independently gates that client-side arbitration and does not become an RMF rule or a source of promo history.
