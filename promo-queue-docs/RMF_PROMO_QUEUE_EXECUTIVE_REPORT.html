RMF rendering under Promo Queue

Cumulative implementation through PR 3, focused on how an already-selected New Tab Page RMF becomes one authorized, physically rendered card.

Reviewed: 13 Aug 2026 PR heads: 6087 fdb31d0 · 6194 475f110 · 6291 1f115b8 Final code: bartosz/promo-q-3
Executive conclusion. RMF remains the authority for campaign configuration, targeting, scheduled-message selection, dismissal, and ordinary shown state. When promoPresentationCoordination is enabled, Promo Queue becomes the authority for when and which physical NTP host may publish that selected candidate. When disabled, the previous direct/eager RMF path is preserved.
Unchanged

RMF product policy

Shared selection, targeting, campaign config, dismissal, and shown/unique-shown storage are not moved into Promo Queue.

Changed

Physical publication

One app-scoped service authorizes exactly one registered NTP renderer and owns handoff through verified removal.

Operational

Timing and proof

Confirmed appearances create directional cooldown history; time alone never retries; missing removal proof fails closed.

Unchanged RMF responsibilities

The cumulative stack does not change the shared RMF engine or HomePageConfiguration. Promo Queue receives the result of existing selection and adds only presentation coordination plus a separate cooldown timestamp. S1

Selection & targeting

Scheduled NTP message lookup, surface matching, afterIdle/noTrigger filtering, onboarding suppression, targeting, and campaign configuration remain upstream.

Dismissal & actions

RMF dismissal still updates the shared store and emits its change notification. Existing action handling, image loading, and action/dismiss pixels remain in the NTP/RMF path.

Shown state

remoteMessageShown, remoteMessageShownUnique, and shared shown-state persistence remain in HomePageConfiguration.didAppear. Atomic unique-shown reservation remains out of scope.

Who owns what now

NewTabPageMessagesModel is now both a candidate client and a service-controlled physical renderer. In coordinated mode it keeps ordinary local placeholders direct, but suppresses RMF from the published collection until showRemoteMessage authorizes a specific presentation. It then constructs the existing HomeMessageViewModel, publishes a presentation-keyed render item, and lets NewTabPageView render it. S2 S5

The coordinated RMF transaction

Identity is layered by lifetime

  • Renderer ID: stable NTP model/surface.
  • Registration generation: one attachment epoch; stale generations cannot mutate replacements.
  • Logical session: session UUID + message ID; owns the global lease.
  • Presentation ID: one physical authorization within that session.
  • Removal ID: one exact outgoing hide operation.

Same message, two cases

  • Payload update on one renderer: rebuild the view model while preserving the presentation and SwiftUI row identity.
  • Handoff to another renderer: retain logical session + lease, remove the outgoing card, then mint a new presentation for the successor.
  • If no matching renderer is eligible at settlement, end the session; a later return must pass cooldown as a new session.

How exactly one physical NTP renderer wins

Each standard-NTP, suggestion-tray/favorites, and unified-input/favorites model registers independently. The host layer orders exposure changes; the service is the final serialization boundary. There is no hard-coded host-type priority. S6 S7

Eligibility predicate

Loaded, not torn down, owner active, render location ready, explicitly visible, not covered, and attached to a window.

Ordered host exposure

Deactivate outgoing before showing incoming; hide hosted surface before reactivating standard NTP. Stale async tray completions carry a generation guard.

Service backstop

If multiple registrations are nevertheless eligible, the service picks the first in stable registration order and holds only one owned presentation.

Directional spacing

  • Confirmed modal → next RMF: 10 minutes.
  • Confirmed RMF → next RMF session: 10 minutes.
  • Confirmed RMF → next modal: 24 hours.
  • Modal → modal remains existing modal policy.

RMF admission uses the later applicable modal or RMF history boundary. Same-session handoff is not a new admission. S8

Checkpoint-only reconsideration

Cooldown expiry schedules nothing. A blocked, still-reported candidate is retried only after a real checkpoint:

  • RMF configuration notification, refresh, or candidate update;
  • registration, eligibility, attachment, visibility, or host-exposure change;
  • foreground interaction readiness/reactivation;
  • modal-owner release or exact RMF removal settlement.

Physical removal and failure behavior

iOS 17+

Animated, native completion

Clear the authorized source inside withAnimation(..., completionCriteria: .removed). SwiftUI uses scale + opacity for removal; only native completion reports .animationCompleted.

iOS 15 / 16

Synchronous, no animation

Clear inside a transaction with animations disabled and use an identity transition. After verifying the source is clear, report .sourceRemovedWithoutAnimation.

Fail closed means collision safety wins over availability. Stale or mismatched generation/session/presentation/removal callbacks are ignored. Unverified detachment, a missing terminal, unexpected selected-renderer loss, or an inconsistent authorization rejection retains the global owner. That can block all coordinated promos for the process, but it prevents a successor or modal from appearing while old RMF pixels may still exist. S2 S4

Feature-flag routing

What future RMF/NTP work must preserve

Renderer contract

  • Never publish coordinated RMF before service authorization.
  • A failed showRemoteMessage must mean no coordinated content was published.
  • Carry exact generation, session, presentation, and removal identities through callbacks.
  • Do not release via onDisappear, a guessed delay, or cooldown passage.
  • Explicitly deregister only after removal or verified physical detachment.

Host contract

  • Use the shared exposure predicate; window attachment alone is insufficient.
  • Perform outgoing-before-incoming handoff whenever a host or overlay covers an attached NTP.
  • Invalidate stale async host completions with generation identity.
  • Preserve one app-scoped service/arbiter graph and checkpoint-driven retry.
  • Exercise standard NTP, suggestion tray, and unified input when changing rendering or removal.

Glossary

Candidate
An upstream-selected NTP RMF known to a renderer; not permission to publish.
Renderer
One physical NTP model/host capable of displaying an RMF card.
Registration generation
One renderer attachment epoch used to reject callbacks from an older registration.
Logical session
One global RMF ownership lifetime for a message; it may span physical hosts.
Presentation
One authorization to one renderer within a logical session.
Draining
The state in which the session and lease remain held while outgoing pixels are removed.
Removal terminal
Verified evidence that one exact outgoing presentation can no longer contribute visible pixels.
Settlement turn
One following main-queue turn after terminal evidence, before transfer or release.
Appearance confirmation
Service acceptance that an exact authorized presentation is current, eligible, and attached.
Ordinary accounting
Existing RMF shown pixel, unique-shown check, and shown-state update.
Checkpoint
A real state change that asks the service to reconsider work; time passage alone is not one.
Fail closed
Retain ownership when disappearance cannot be proven, preventing possible promo overlap.
